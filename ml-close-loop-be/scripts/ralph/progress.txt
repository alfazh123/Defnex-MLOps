## Codebase Patterns

- SQLite dev DB (`data/app.db`, gitignored) is stale between iterations — after
  adding models, `alembic upgrade head` must be run *before*
  `alembic revision --autogenerate` on a fresh checkout, or autogenerate fails
  with "Target database is not up to date."
- `list[str]`-typed columns need an explicit `mapped_column(JSON, ...)` —
  SQLAlchemy 2.0's `Mapped[list[str]]` has no default type-map entry (unlike
  `dict`, which maps to JSON automatically), so a bare `mapped_column()` fails.
- Domain models live in one file per entity under `app/models/`, exported
  from `app/models/__init__.py` (which `alembic/env.py` imports) so Alembic
  autogenerate picks them up. Follow this per new entity.
- `tests/conftest.py` provides a `db_session` fixture: in-memory SQLite engine
  (`create_engine("sqlite://")`), tables created from `Base.metadata`, one
  fresh DB per test. Use this for all service-layer tests instead of hitting
  `data/app.db`.
- ORM models are flat (columns match the manifest fields 1:1); API response
  schemas (e.g. `DatasetVersion`) nest a sub-object (`manifest`). Services own
  the flat<->nested mapping via a `to_schema()` helper in the service module —
  don't try to make Pydantic's `from_attributes` do this automatically across
  a structural mismatch.
- Service functions take ORM/domain identifiers (e.g. `dataset_id: str`) and
  return ORM model instances, not schemas — schema conversion is a separate,
  explicit step (`to_schema`), kept out of the API layer's concern. Exception:
  composed/aggregate views with no matching ORM entity (e.g. `list_datasets`
  for `GET /datasets`) return the response schema directly from the service.
- Standard error envelope (PRD §18, openapi.yaml `Error` schema) is
  `{"error": {"code": ..., "message": ...}}` — NOT FastAPI's default
  `{"detail": ...}`. Pattern: raise `app.api.errors.APIError(status_code,
  code, message)` from any endpoint; a global `HTTPException` handler in
  `app/main.py` serializes its `detail` dict as-is instead of wrapping it
  again. Reuse `APIError` for every future domain's error responses instead
  of raising bare `HTTPException`.
- API-level tests (hitting routes via `TestClient`, not calling service
  functions directly) need a `create_engine("sqlite://", ...,
  poolclass=StaticPool)` + `app.dependency_overrides[get_db]` fixture —
  plain `"sqlite://"` without `StaticPool` gives each new connection a
  *separate* empty in-memory DB, so `Base.metadata.create_all` runs against
  a table the request handler's own connection can't see ("no such table").
  The `db_session` fixture in `conftest.py` (single `Session` object, no
  pooling concern) is fine for service-layer tests but insufficient for
  this pattern.

    `processed/{dataset_id}/{version}/` (Phase 1 explicitly says "Validation belum perlu
    diimplementasikan penuh pada phase ini" and no intake/normalization story exists — see US-002's
    prior note). The service therefore takes `records` as an explicit in-memory parameter instead of

    `POST .../validate` endpoint (US-006) is deferred to that story.

- **openapi.yaml's 409 case ("dataset version has not completed `split`, or `model_id` cannot be
  resolved") is deliberately NOT enforced** - same "not-yet-built pipeline" scope decision as
  US-008's note: no `split` status exists anywhere in this codebase's `DatasetVersion.status`
  values, and no Model registry exists yet to resolve `model_id` against (US-011, next story, adds
  it). `POST /training-runs` therefore only checks that the `(dataset_id, dataset_version)` pair
  exists (404), matching what's actually buildable today; the endpoint's request/response schemas
  are unchanged from openapi.yaml so nothing here blocks wiring the 409 checks once US-011 lands.
- `training_service.create_training_run` only `db.flush()`es (established in US-008, since the
  worker owns its own `db.commit()`); the new API endpoint calls `db.commit()` itself after the
  service call, matching how `dataset_service.create_dataset_version` handles its own commit vs.
  how the worker commits around `process_next_job` - commit ownership sits with whichever caller
  is the actual transaction boundary (HTTP request vs. worker loop), not inside a service function
  shared by both.
- `TrainingRun.model_version` is always `None` in the response for now - the field only gets
  populated once a `COMPLETED` run is registered into the model registry (per openapi.yaml's own
  description on `GET /training-runs/{id}`), and that registry doesn't exist yet (US-011/US-012).
- Files changed: app/api/training.py (new), app/main.py, app/services/training_service.py (added
  `get_training_run`, `to_schema`, aliased schema import), tests/test_training_api.py (new, 5
  tests: 404/201/422 for create, 404/200 for get).
- **Learnings for future iterations:**
  - No models changed this story, so no Alembic migration was needed/run; `alembic upgrade head`
    still run as a no-op sanity check per the quality checklist.
  - When an ORM model and its matching Pydantic response schema share the same class name (e.g.
    both called `TrainingRun`), and a service module needs both, alias the Pydantic import (`as
    TrainingRunSchema`) rather than the ORM one - the ORM name is used far more often within the
    service (type hints on nearly every function) so keeping it unaliased reads better.
  - A 409 case named in openapi.yaml can legitimately stay unenforced across multiple stories in a
    row when it depends on a *different* not-yet-built story (here: US-011's model registry) -
    don't invent a stand-in check; just note which future story is expected to add it, same
    pattern as US-005/US-006/US-008's deferred-pipeline notes.

## [2026-08-28] - US-011
- Added `Model`/`ModelVersion` SQLAlchemy models (`app/models/model.py`) per
  model-artifact-versioning-lineage.md §6/§8: `Model.model_id` (PK, no other columns - a bare
  identity row, same shape as `Dataset`), `ModelVersion` with `model_id` FK, integer `version`
  (unique together), `status` (default `REGISTERED`), `training_run_id` FK to
  `training_runs.training_run_id` (required, non-nullable per §9 Decision 5), `base_model`
  (top-level string column, NOT nested inside `training_config` - explicit known-deviation #3),
  `training_config` (JSON), `artifacts` (JSON list of `{type, uri, size_bytes}` objects - a version
  can accumulate more than one artifact entry over time per §3), `dataset_validation_report_ref`,
  `created_at`, `created_by`, `promotion_decision_ref`, `previous_model_id` (all nullable, matching
  §8's JSON Schema `required` list which only mandates model_id/version/status/training_run_id/
  dataset_id/dataset_version/created_at/artifacts).
- **No `evaluation_id` field added** - matches this story's explicit AC; evaluation fields
  themselves are also NOT added yet (`eval_loss_trend`/`qualitative_comparison`/
  `general_domain_regression_check`) since US-014 ("Add evaluation persistence...") owns adding
  those to this same record per its own AC ("Evaluation fields persisted on the model version
  record"). Adding them now would pre-empt that story's scope.
- **`dataset_id`/`dataset_version` are NOT stored as columns on `ModelVersion`** - same
  flat-ORM/derived-nested pattern as `ValidationReport`/`TrainingRun`: they're reachable via
  `ModelVersion.training_run_id -> TrainingRun.dataset_version_id -> DatasetVersion.dataset_id/
  version` (a 2-hop relationship chain), so storing them again on `ModelVersion` would be
  redundant denormalization the doc's own schema doesn't actually require as separate storage -
  only as *returned* API fields, which a `to_schema()` helper derives (deferred to US-012/US-013,
  same split used by every prior domain's service layer).
- **`promotion_decision_ref` is a plain nullable string, not a FK** - `PromotionDecision` doesn't
  exist as a table yet (US-015), and the doc's own schema (§8) types this field as
  `["string", "null"]`, not a foreign key - consistent with how it's meant to be set later by
  US-016's promotion service, not enforced by the DB schema now.
- Files changed: app/models/model.py (new), app/models/__init__.py,
  alembic/versions/29f1f96e3ea1_us_011_add_model_and_model_version_.py (new).
- **Learnings for future iterations:**
  - No dedicated test file added - pure model+migration story, same precedent as US-001/US-004/
