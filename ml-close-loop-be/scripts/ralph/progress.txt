## Codebase Patterns

- SQLite dev DB (`data/app.db`, gitignored) is stale between iterations — after
  adding models, `alembic upgrade head` must be run *before*
  `alembic revision --autogenerate` on a fresh checkout, or autogenerate fails
  with "Target database is not up to date."
- `list[str]`-typed columns need an explicit `mapped_column(JSON, ...)` —
  SQLAlchemy 2.0's `Mapped[list[str]]` has no default type-map entry (unlike
  `dict`, which maps to JSON automatically), so a bare `mapped_column()` fails.
- Domain models live in one file per entity under `app/models/`, exported
  from `app/models/__init__.py` (which `alembic/env.py` imports) so Alembic
  autogenerate picks them up. Follow this per new entity.
- `tests/conftest.py` provides a `db_session` fixture: in-memory SQLite engine
  (`create_engine("sqlite://")`), tables created from `Base.metadata`, one
  fresh DB per test. Use this for all service-layer tests instead of hitting
  `data/app.db`.
- ORM models are flat (columns match the manifest fields 1:1); API response
  schemas (e.g. `DatasetVersion`) nest a sub-object (`manifest`). Services own
  the flat<->nested mapping via a `to_schema()` helper in the service module —
  don't try to make Pydantic's `from_attributes` do this automatically across
  a structural mismatch.
- Service functions take ORM/domain identifiers (e.g. `dataset_id: str`) and
  return ORM model instances, not schemas — schema conversion is a separate,
  explicit step (`to_schema`), kept out of the API layer's concern. Exception:
  composed/aggregate views with no matching ORM entity (e.g. `list_datasets`
  for `GET /datasets`) return the response schema directly from the service.
- Standard error envelope (PRD §18, openapi.yaml `Error` schema) is
  `{"error": {"code": ..., "message": ...}}` — NOT FastAPI's default
  `{"detail": ...}`. Pattern: raise `app.api.errors.APIError(status_code,
  code, message)` from any endpoint; a global `HTTPException` handler in
  `app/main.py` serializes its `detail` dict as-is instead of wrapping it
  again. Reuse `APIError` for every future domain's error responses instead
  of raising bare `HTTPException`.
- API-level tests (hitting routes via `TestClient`, not calling service
  functions directly) need a `create_engine("sqlite://", ...,
  poolclass=StaticPool)` + `app.dependency_overrides[get_db]` fixture —
  plain `"sqlite://"` without `StaticPool` gives each new connection a
  *separate* empty in-memory DB, so `Base.metadata.create_all` runs against
  a table the request handler's own connection can't see ("no such table").
  The `db_session` fixture in `conftest.py` (single `Session` object, no
  pooling concern) is fine for service-layer tests but insufficient for
  this pattern.

    `processed/{dataset_id}/{version}/` (Phase 1 explicitly says "Validation belum perlu
    diimplementasikan penuh pada phase ini" and no intake/normalization story exists — see US-002's
    prior note). The service therefore takes `records` as an explicit in-memory parameter instead of

    `POST .../validate` endpoint (US-006) is deferred to that story.

## [2026-08-28] - US-018
- Added `Deployment` SQLAlchemy model (`app/models/deployment.py`) per PRD §15's minimal field
  list exactly: `deployment_id` (string PK), `model_id`, `model_version`, `environment`, `status`,
  `deployed_at`. Deliberately no `ForeignKey` to `models`/`model_versions` (plain `String`/
  `Integer` columns for `model_id`/`model_version`) - this story's own AC requires "no foreign
  dependency that would merge it with the model registry's own status field," matching PRD §12's
  explicit "Model Registry dan Deployment harus tetap menjadi dua konsep berbeda."
- **Noted, not blocking:** openapi.yaml's `DeploymentStatus`/`DeployResult` schemas describe a
  single model-level *pointer* (`model_id`, `current_deployed_version`, `deployed_at`, `status` -
  no `environment` or `deployment_id` in the response) rather than a row-per-deployment history
  table with `environment`. This is not a doc-vs-doc conflict to stop on: this story's AC only
  asks for the underlying table's columns (PRD §15's list, which does include `environment`/
  `deployment_id`), not the API response shape - that mapping is US-019's concern. The table can
  hold more than any single response schema exposes, same as every prior flat-ORM/derived-schema
  domain (see Codebase Patterns).
- Files changed: app/models/deployment.py (new), app/models/__init__.py,
  alembic/versions/eb8695aecf69_us_018_add_deployments_table.py (new).
- **Learnings for future iterations:**
  - US-019 (deploy service/API) will need to decide how `Deployment` rows map to the
    `DeploymentStatus`/`DeployResult` pointer views - likely "latest deployments row per
    model_id/environment" rather than a live FK-backed relationship, keeping the no-FK
    decoupling from this story intact.
  - When writing a small JSON edit script inline (e.g. flipping `prd.json`'s `passes` field) with
    Python's `json.dump`, pass `ensure_ascii=False` - the default silently escapes existing
    non-ASCII characters already in the file (e.g. `§` section signs used throughout this PRD's
    acceptance criteria) into `\uXXXX` sequences, producing a huge, unrelated-looking diff across
    the whole file instead of the single intended field change.
